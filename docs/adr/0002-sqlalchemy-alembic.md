# ADR-0002: SQLAlchemy + Alembic instead of SQLModel

## Context

The specification proposes SQLModel as the ORM, which uses one class as both the database
table and the API schema. The schema will keep changing during development, so we need
versioned migrations and full access to the ORM's features.

## Decision

Use **SQLAlchemy 2.0** for the database models and **Alembic** for migrations. Pydantic
schemas for the API stay separate from the database models.

Why:

1. **Tables and the API can evolve independently** - what we store doesn't have to match
   what the API returns.
2. **Alembic is built for SQLAlchemy** - migrations can be autogenerated from the models.
3. **One less layer** - SQLModel sits on top of SQLAlchemy anyway, lags behind its releases
   and is less documented.

## Consequences

- Every schema change goes through an Alembic migration.
- Converting between database models and API schemas is an explicit step.

## Alternatives considered

- **SQLModel (spec)** - convenient for simple CRUD, but couples tables to API schemas.
- **Raw SQL** - full control, but no models and no autogenerated migrations.
